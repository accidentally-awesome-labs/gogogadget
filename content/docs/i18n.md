i18n is zero-dependency (beyond `golang.org/x/text`, already in the tree):
a detection middleware, a per-request printer, and Go catalogs. English and
Spanish ship; content (blog/docs markdown) stays English this round — that
boundary is deliberate and documented below.

## Detection order

`i18n.Detect` sits in the global chain (between `accessLog` and `rateLimit`)
and resolves every request's locale in priority order:

1. `?lang=es` query parameter (session-only — never persisted),
2. the `ggg_lang` cookie (written only by `POST /set-locale`),
3. the `Accept-Language` header (via `language.MatchStrings`),
4. English (the matcher default).

The resolved `language.Tag` and its `message.Printer` live in the request
context. Inside every templ component `ctx` is already in scope (templ binds
it from the component input), so templates need no signature changes to call
`i18n.T`.

## T() and the key scheme

```go
i18n.T(ctx, "nav.projects")                          // plain lookup
i18n.T(ctx, "projects.usage", used, limit, planName) // fmt verbs
```

Keys are namespaced `<area>.<name>` (`nav.*`, `sidebar.*`, `home.*`,
`projects.*`, `settings.*`, `billing.*`, `admin.*`, `activity.*`, `api.*`,
`errors.*`, `common.*`, `email.*`, `legal.*`, `i18n.*` …). A missing
translation can never silently render as a legitimate string: `T` returns the
key itself when the locale lacks it, retries English, and only then gives up
— namespaced keys make the failure a visible bug instead of a wrong sentence.

Catalogs are plain Go files: `internal/i18n/catalog_en.go` and
`catalog_es.go`, each an `init()` of `message.SetString` calls. English
values are the exact former template strings, moved verbatim.

## The switcher

`templates.LocaleSwitcher(path)` (a `<details>` dropdown — no JS, CSP-safe)
mounts in the public footer and the app sidebar. Each locale is a small
`hx-post="/set-locale"` form carrying `lang` and `returnTo`:

- `lang` is validated against the supported set (anything else → 422),
- `returnTo` must start with `/` and not `//` (protocol-relative → off-origin
  is rejected; anything else falls back to `/`),
- the handler sets `ggg_lang` (1 year, HttpOnly, SameSite=Lax, Secure in
  production) and issues a **hard redirect** — locale changes the *shell*,
  which boosted navigation never re-renders.

`/set-locale` is a public route on the main mux, so the full chain — CSRF
included — applies; the switcher's htmx forms ride the body-inherited
`X-CSRF-Token` header.

## Users table

`users.locale` (TEXT, `''` = English) is the per-user preference slot. The
welcome email already reads it (`mail.WelcomeMessage(locale, …)`); a future
sync from Clerk's locale attribute would land in the `user.*` webhook parsers
(`internal/identity`), not here. Billing emails pass English explicitly this
round.

## What is NOT translated

- Blog and docs markdown (all `content/` stays English this round).
- `Page.Title` values composed by handlers (the document `<title>` suffix is
  the product name; handler-side strings like toast messages stay English).
- Date layout strings (`January 2, 2006`) and plan feature bullets (data from
  `plans.go`, not template literals).

## Add a locale

1. Copy `catalog_es.go` → `catalog_<lang>.go`, translate every key.
2. Add the tag to the matcher in `internal/i18n/i18n.go` (`language.NewMatcher`
   list) and an entry to `Locales` (code + native label) — the switcher picks
   it up automatically.
3. Extend `ParseSupported` coverage automatically (it iterates `Locales`).

That's the whole recipe — detection, fallback, and the switcher are
tag-count-agnostic. See [Extending GoGoGadget](/docs/extending) for the
recipe index.

## Where the locale comes from

Precedence, highest first:

1. **`?lang=`** — a deliberate per-request override. Never persisted, so the
   next plain request returns to the stored choice.
2. **`users.locale`** — written by the switcher for signed-in users. This is
   what makes a choice follow someone to a new device, and it is the only
   locale an email can read (there is no `Accept-Language` header in a job).
3. **The `ggg_lang` cookie** — how signed-out visitors keep a choice.
4. **`Accept-Language`**, then English.

Steps 1, 3 and 4 are resolved by `i18n.Detect`, which runs early in the chain
— before the session is known. Step 2 is applied in `sessionLoad`
(`applyStoredAppearance` in `internal/web/appearance.go`), because the user
row does not exist until the session loads. When the row and the cookie
disagree the cookie is re-synced, so the next request and the pre-paint script
agree with the server.

That re-sync happens on **GET/HEAD only**: a POST to `/set-locale` is the
request that is changing the preference, and syncing there would emit a second
`Set-Cookie` for the same name and leave the outcome to header ordering.

Setting an empty language clears the preference (cookie expired, row set to
`''`) rather than storing `en` — a user asking to follow their browser again
must not end up pinned to English on a Spanish machine.
